2. 데이터 고지와 원본 보존
모든 가상 숫자는 교육용 예시이며 역사적 개표 재현이 아니다. MOCK 100%도 공식 최종 결과와 일치시키지 않는다. 실제 자료의 data_mode=REAL_FINAL, simulated=false, verification_status=REVIEW_REQUIRED를 변경하지 않는다. 참조 snapshot_id는 P1_REAL_FINAL_dd6dba9ecf8b3c6d이다.
공식 결과 확정시각 results_as_of=null, precision=UNKNOWN을 유지한다. 처리시각 2026-11-20T14:24:35+09:00을 결과 확정시각으로 대체하지 않는다.
동작구 상도제3동 관내사전투표의 선거인수 5,049, 투표수 5,050, 기권자수 -1은 사유 미확인이다. 원값 보존과 김형석 독립 검토가 필요하며 이번 문서가 해결·최종 승인하지 않는다.
공식 개표율 count_rate_pct=100은 표시값이며 원본 분모가 없다. 이를 이용해 역사적 중간 개표를 역산하지 않는다.


3. 구조와 접속 주소 — 전부 제안/미구현
Frontend 1 → SYSTEM 1 FastAPI(제어·송출)
SYSTEM 2 FastAPI → SYSTEM 1 WebSocket 구독 → ID·순서·합계 검증 → 가상 저장소 반영 → ACK
Frontend 2 → SYSTEM 2(조회·RAG·기사·검증·사람 승인: 후속 계약)
독립 프로세스로 송출 오류와 뉴스룸 처리를 분리하고 각각 재시작할 수 있게 하는 선택안이다. 단일 서버보다 연결·재동기화 관리가 늘어난다. 저장소 수·DB 제품·배포 방식·작업 일정은 미확정이다.
SYSTEM 1 REST: http://localhost:8001/api/v0.1
SYSTEM 1 WS: ws://localhost:8001/ws/v0.1/simulation?client_role=frontend
SYSTEM 2는 같은 WS에 client_role=system2로 접속하는 서버 측 클라이언트다.
SYSTEM 2 상태: http://localhost:8002/api/v0.1/health, /api/v0.1/ingestion/status
SYSTEM 1 상태: /api/v0.1/health 및 /api/v0.1/simulation/status
Frontend 예상 origin http://localhost:5173은 CORS 허용 후보일 뿐이다. origin·인증·운영 권한 방식은 공동 확인 전이다. localhost 개발 바인딩만 제안하며 외부 배포 명세가 아니다. client_role 문자열만으로 SYSTEM 2 신원을 인증하지 않는다. 실제 구현 시 receiver 자격 검증·연결별 토큰을 별도 정하고 비밀값은 fixture/Drive에 저장하지 않는다.


4. REST 요청과 응답
REST는 버튼을 누를 때 한 번 요청하고 결과를 받는 방식이다. Content-Type: application/json. GET 요청은 본문 없음. POST는 request_id(고유 문자열)를 필수로 받는다. 응답은 JSON이며 성공 {ok:true,request_id,run_id,state,seq}, 실패 {ok:false,request_id,error:{code,message,retryable,details}}를 사용한다.
GET /simulation/status → 200: {ok:true,run_id,state,seq,snapshot,system2,observed_at,data_mode:"MOCK",simulated:true}. snapshot은 최신 snapshot/update의 전체 현재값이다. seq는 마지막 발생 이벤트 순번이며 snapshot.seq와 다를 수 있다.
GET /health → 200 {service:"SYSTEM1",status:"UP",observed_at}; 프로세스 생존만 의미하며 SYSTEM 2 수신 성공을 뜻하지 않는다. 초기화/내부 장애로 처리 불가능하면 503 status=NOT_READY.
POST /simulation/start:
{"request_id":"MOCK_CMD_START","expected_run_id":"MOCK_RUN_A","election_id":"0020260603","election_type":"GOVERNOR","scenario_id":"MOCK_SEOUL_10000_V01","data_mode":"MOCK","simulated":true}
200 성공. IDLE→RUNNING, PAUSED→같은 run 이어서 RUNNING. RUNNING 중 새로운 start는 409 ALREADY_RUNNING. 완료 뒤 재시작은 reset 필요.
POST /simulation/stop:
{"request_id":"MOCK_CMD_STOP","expected_run_id":"MOCK_RUN_A"}
200 RUNNING→PAUSED. PAUSED/IDLE이면 현재 상태 그대로 200. 누적값과 run_id 유지. 이미 송출된 데이터는 삭제하지 않는다. 한 이벤트 반영을 원자적으로 끝낸 뒤 멈추므로 stop 직전 update는 도착할 수 있다.
POST /simulation/reset:
{"request_id":"MOCK_CMD_RESET","expected_run_id":"MOCK_RUN_A"}
200 어느 상태에서나 새 run_id, seq=1, state=IDLE, 0표 snapshot. 진행 중이면 먼저 생성 작업을 원자적으로 중단한다. 이전 run의 이벤트/감사 로그는 보존한다. 현재 화면만 새 run으로 교체한다. 새 snapshot ACK 전 SYSTEM 2를 SYNCED로 표시하지 않는다.
처음 서버 준비 시 IDLE run과 seq=1 snapshot을 만든다는 제안이다. 재시작은 새 run으로 시작하며 복구 재생은 v0.1 범위 밖이다.
동일 request_id·동일 본문 재시도는 같은 결과를 반환하며 두 번 reset/start하지 않는다. 동일 ID·다른 본문 409 REQUEST_ID_CONFLICT. 이력은 해당 서버 수명 동안 보관하는 제안이며 재시작 이후 재시도 보장은 미정이다.
expected_run_id 불일치 409 RUN_MISMATCH, JSON/필드/선거·지역·후보 오류 422 VALIDATION_ERROR 또는 UNKNOWN_ID, REAL_FINAL 요구 422 UNSUPPORTED_DATA_MODE, 미인증 401, 권한 없음 403, 서버 장애 503 SERVICE_UNAVAILABLE. 오류 응답에는 내부 비밀·스택을 노출하지 않는다. 오류 상세 expected/observed는 가능한 경우만 제공한다. 실패한 제어 요청은 상태·run·seq를 변경하지 않는다.
상태 enum: IDLE(초기값), RUNNING(생성 중), PAUSED(중지), COMPLETED(교육용 100%), ERROR(생성·검증 중단). ERROR에서 start는 409 RESET_REQUIRED, reset으로 복구한다. SYSTEM 2 연결 실패 시 v0.1은 생성도 멈추고 ERROR로 전환하는 제안이다. 버퍼 자동 재송출은 제공하지 않는다.


5. WebSocket 이벤트와 공통 필드
WebSocket은 연결을 유지해 서버가 변화를 보내는 통로다. 연결 직후 최신 전체 snapshot, 이후 update/status/error를 보낸다. 전송 문자열은 한 메시지당 JSON 객체 하나다. fixture의 scenarios 배열 포장은 파일용이며 WS에 그 포장을 보내지 않는다.
공통 필수: contract_version="0.1", contract_status="PROPOSAL_UNIMPLEMENTED", type, election_id(문자열), election_type="GOVERNOR", run_id(문자열), seq(1 이상 정수), event_time/emitted_at(ISO8601 +09:00), data_mode="MOCK", simulated=true, notice, reference.
reference는 source_snapshot_id, dataset_version, verification_status="REVIEW_REQUIRED", results_as_of=null, results_as_of_precision="UNKNOWN", source_ids를 포함한다. source_ids는 실제 자료의 출처이며 가상 숫자의 공식 근거를 뜻하지 않는다.
run_id는 한 재생 회차, seq는 그 회차에서 발생한 모든 이벤트의 전역 증가 번호다. snapshot/update/status/error는 서로 같은 순번을 쓰지 않는다. 조회·재접속용 snapshot 재전송은 저장된 데이터 버전의 기존 seq를 유지하므로 새 이벤트가 아니다. status/error만 갱신된 경우 snapshot의 seq는 최신 전역 seq보다 작을 수 있다.
event_time은 가상 시나리오 기준시각, emitted_at은 실제 송출시각이다. fixture의 두 시각은 설명용 가상 시각이다. 관측시각 observed_at·ACK 수신시각은 실제 서버 시계이며 시간초과 판정은 서버 단조 시계를 사용한다. election_date·processed_at·results_as_of와 혼동하지 않는다.
snapshot: state, snapshot_id, scope_region_ids, regions(범위 내 전체 누적값), catalog(후보·지역 사전)를 제공한다.
update: state, snapshot_id, scope_region_ids, regions(범위 내 전체 누적값)을 제공한다. 차이값이 아니므로 덧셈하지 않고 교체한다. catalog는 snapshot에서 받는다. 최신 update 값으로 재접속 snapshot을 만들 수 있다.
status: state, reason, 필요 시 system2. 오류가 아니어도 시작/중지/수신상태 변화를 알린다.
error: state, error{code,message,retryable,details}, last_good_snapshot_id. 검증 실패 데이터는 화면의 정상 수치를 덮어쓰지 않는다.
snapshot_id="MOCK_RUN_A_S3" 같은 새 가상 ID를 사용한다. 이는 reference.source_snapshot_id와 별개다.


6. 후보·지역·단위·분모
election_id="0020260603"은 앞자리 0을 보존하는 문자열이며 election_type과 함께 사용한다.
candidate_id는 기존 0020260603_SEOUL_C01(정원오), C02(오세훈), C04(김정철), C05(유지혜), C07(권영국)이다. C03/C06을 만들거나 연속 번호로 재명명하지 않는다. 후보·지역 ID는 내부 키이며 공식 후보 ID/행정코드가 아니다.
region_id=SEOUL 및 SEOUL_D01~D25는 fixture catalog.regions의 실제 매핑을 그대로 사용한다. D01=종로구, D20=동작구다. 이름 정렬로 ID를 다시 부여하지 않는다.
regions 각 행: region_id, target_ballots(1 이상 정수·표), target_ballots_basis, counted_votes/valid_votes/invalid_votes(0 이상 정수·표), count_rate_pct(number·%), candidate_votes[{candidate_id,votes(정수·표),vote_share_pct(number|null·%)}].
v0.1 fixture 범위는 SEOUL 전체 하나이며 서울 전체 교육용 목표 10,000표를 임의 설정했다. 이는 공식 ballots_cast도 공식 개표율 분모도 아니다. target_ballots_basis="SCENARIO_FIXED_EDUCATIONAL". 구별 수치는 아직 제공하지 않으므로 구 화면에는 자료 없음으로 표시한다. catalog에 지역이 있다고 개표 수치가 있는 것은 아니다.
counted_votes=valid_votes+invalid_votes. valid_votes=후보 5명 votes 합.
count_rate_pct=counted_votes/target_ballots×100. vote_share_pct=votes/현재 valid_votes×100. 백분율 범위 0~100, 계산값 소수 6자리 HALF_UP, 화면은 2자리 권장. valid_votes=0이면 vote_share_pct=null(아직 분모 없음), 0%로 꾸미지 않는다.
정상 예: [1000,900,40,30,30] 합=2000, 무효=20, 집계=2020, 개표율=20.2%, 득표율=[50,45,2,1.5,1.5]%.
공식 turnout_pct=ballots_cast/electors×100이며 개표율과 다르다. MOCK에서는 투표율·electors·abstentions를 생성하지 않는다. 공식 표시 득표율은 소수 2자리 DOWN, 공식 투표율은 1자리 HALF_UP, 정제 재계산 비율은 6자리 HALF_UP이라는 원 사전을 보존한다. MOCK 비율을 official_* 필드로 보내지 않는다.
CITY와 25개 DISTRICT를 함께 더하지 않는다. 추후 구별 제공 시 각 구 target_ballots 합=서울 목표, 구별 후보·유효·무효 합=서울 값으로 검증한다. 후보결과에 반복된 valid_votes/개표율을 후보끼리 더하지 않는다.
음수, NaN, 문자열 숫자, 미등록 ID, 후보 누락/중복, 집계>목표, 합계 불일치, 정상 진행 중 후보 누적 감소는 거부한다. v0.1 정정 이벤트는 지원하지 않으며 오류→reset 또는 후속 계약으로 처리한다.


7. SYSTEM 2 건강상태와 ACK
연결됨은 소켓 접속일 뿐이다. SYSTEM 2가 검증하고 저장소에 원자적으로 반영한 snapshot/update에만 result="APPLIED" ACK를 보낸다. status/error에는 ACK하지 않는다.
ACK 필드: type="ack", receiver_id, receiver_instance_id(프로세스별), connection_id(S1이 인증된 연결에 부여), run_id, acked_seq, snapshot_id, result="APPLIED", received_at, applied_at, data_mode="MOCK", simulated=true. fixture 값은 모두 가상 증빙이다. 서버가 현재 연결·receiver·run·송신 데이터 seq/snapshot을 대조한다. FE가 보내는 ACK나 미래 seq/다른 run/다른 연결 ACK를 인정하지 않는다.
중복 ACK는 같은 버전이면 무시한다. ACK가 뒤로 가면 상태를 역행시키지 않는다. 저장 실패·검증 실패는 APPLIED 금지, error 및 재동기화 요청으로 처리한다.
S2 heartbeat는 5초마다 {type:"heartbeat",receiver_id,receiver_instance_id,connection_id,run_id}를 보내고 S1이 실제 수신시각을 기록한다. heartbeat는 저장 성공 증명이 아니다.
system2: transport=CONNECTED|DISCONNECTED; receiver_state=AWAITING_ACK|SYNCED|LAGGING|STALE|DISCONNECTED; receiver_id/receiver_instance_id/connection_id/run_id; last_sent_seq(마지막 snapshot/update 순번), last_acked_seq(마지막 적용된 데이터 순번), last_ack_at, last_heartbeat_at, ack_lag_events(미확인 데이터 버전 개수), ack_timeout_ms=10000, heartbeat_timeout_ms=15000, evidence_mode=LIVE|FIXTURE, live_verified(boolean).
ack_lag_events는 seq 차이가 아니다. status/error도 seq를 사용하므로 아직 ACK하지 않은 데이터 버전 개수로 계산한다. ACK 전은 last_acked_seq/last_ack_at/ack_lag_events=null. SYNCED는 현재 run의 최신 데이터 ACK 일치와 heartbeat 15초 이내가 모두 필요하다. 미ACK 최신 데이터가 있으면 LAGGING, 10초 초과하면 STALE. 초기 ACK 전은 AWAITING_ACK, close 감지/heartbeat 15초 초과는 DISCONNECTED. 멈춘 동안 update가 없으면 heartbeat가 건강상태를 유지한다.
live_verified=true는 evidence_mode=LIVE이며 위 SYNCED 조건을 실제 관측했을 때만 허용한다. fixture는 SYNCED 예시라도 FIXTURE/false이므로 “실제 SYSTEM 2 수신 확인” 표시 금지.
GET SYSTEM 2 /ingestion/status → 200 {service:"SYSTEM2",transport,run_id,last_applied_seq,snapshot_id,last_applied_at,verification_state,storage_state,observed_at}. /health는 생존만 확인한다. S1 ACK와 S2 저장 상태를 같은 run/snapshot으로 비교할 수 있게 한다. 이 경로/응답도 제안·미구현이며 fixture 안의 ACK가 실제 연결 시험 결과는 아니다.


8. 누락·재접속·초기화 UI
같은 run에서 중복/역행 이벤트는 재적용하지 않는다. seq 누락을 감지하면 임시 갱신 중지→소켓 재접속→최신 전체 snapshot으로 교체한다. snapshot은 현재까지의 데이터 상태를 포괄하므로 중간 status를 놓쳐도 복원할 수 있다. 전송 이력 재생은 v0.1에 없다. 이후 새로운 이벤트 번호부터 검사한다.
재접속은 1/2/4/8초 후 최대 10초 간격의 지연 재시도 제안이다. 마지막 정상값을 유지하되 “연결 끊김/오래된 자료”와 마지막 시각을 표시한다. 0표로 위장하지 않는다.
run이 바뀐 snapshot은 seq가 1이어도 새 실행으로 전면 교체한다. 기존 run 이벤트·ACK는 버린다. 모르는 run의 update만 먼저 오면 적용하지 않고 snapshot을 요청한다.
S1-S2 단절은 S1 status로, FE-S1 단절은 브라우저 WebSocket close/error 로컬 상태로 표시한다. 끊어진 소켓으로 error JSON을 받을 수 있다고 가정하지 않는다.
시작/중지/초기화 버튼은 요청 중 중복 클릭을 막고 서버 응답으로 확정한다. reset은 새 run과 0표·null 득표율·ACK 대기 표시를 동시에 적용한다.


9. Fixture 사용법과 확인 범위
첨부 JSON은 metadata/catalog/scenarios.normal/error/disconnected/reset 구조다. normal.frames는 snapshot→start status→누적 update→ACK status이며 stop 응답/상태도 있다. error는 REST 422, 고의 합계 오류 입력과 거부 error를 포함한다. disconnected는 S1-S2 상태와 FE 로컬 끊김을 구분한다. reset은 요청·응답·새 run snapshot을 제공한다. 각 시나리오는 독립 UI 사례로 로드하며 전체 파일을 하나의 연속 송출 기록으로 해석하지 않는다.
Frontend는 scenarios의 frames 또는 frame을 실제 수신 이벤트처럼 한 개씩 주입한다. 잘못된 incoming update는 검증 거부 사례 입력이며 정상 데이터로 표시하지 않는다.
이번 확인: JSON 파싱, 기존 ID 참조, 정상/초기화 합계·분모·비율, 필수 가상 고지와 원본 REVIEW_REQUIRED 보존을 정적 확인한다. FastAPI/REST/WS/DB/브라우저 통합은 NOT TESTED이며 실제 수신 성공을 주장하지 않는다.


10. 공동 확인 요청과 다음 단계
김형석 확인: 필드·enum·화면 표시 적합성, 서울 전체 우선/구별 자료 없음 처리, 버튼 상태·reset 동작, 두 Backend 선택안·포트/경로, 수신 지연 임계값·인증/CORS 정책.

11. 재접속 동기화 기준 보충
snapshot에는 sync_cursor_seq(스냅샷을 원자적으로 만든 시점의 최신 전역 이벤트 순번)를 추가한다. 데이터 버전 seq는 기존 값을 보존하고, 수신 측은 sync_cursor_seq 다음 번호부터 누락을 검사한다. ACK의 acked_seq는 데이터 버전 seq를 사용한다. 예를 들어 최신 데이터 seq=3, 최신 status seq=4이면 재접속 snapshot은 seq=3, sync_cursor_seq=4이고 다음 새 이벤트는 5다. 서버는 snapshot 전송과 이후 구독 사이의 누락이 없도록 원자적 구독 경계를 보장해야 한다. REST status 응답의 seq도 같은 관측 시점의 전역 순번이다. 이 규칙 역시 제안/미구현이다.
